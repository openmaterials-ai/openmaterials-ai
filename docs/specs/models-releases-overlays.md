# Model records, code releases, private overlays

Status: accepted design, 2026-10-03, for openmaterials-ai 0.2.0; overlays and
retraction follow in 0.2.1. Basis: main at f7e8655 (0.1.3). Delivered in three
library changes (section 9).

OpenMaterials is the reference for the map's nodes and representations, for
the released versions of the codes they describe, and for the models those
codes read. This document specifies how models and code releases are
registered, how a record cites them, and how an organization extends the map
privately without forking it.

## 0. Principles

1. Two registries, two identities. A code is software that runs: its identity
   is its name and release. A model is parameters a code consumes: its
   identity is its content.
2. Identity is format; registration is publication. Any record may cite any
   content hash. Registering an entry in the public commons publishes it; the
   bytes of an unregistered entry stay with their owner (or the host the owner
   chooses).
3. Raw artifacts are never ingested (GOVERNANCE.md, "Data ownership and
   fairness"): the commons stores metadata, hashes and pointers, never weights
   or trajectories.
4. Add-only and content-addressed, as the map log already is and the
   configuration layer is for its uid and provenance (its `external_ids` is
   overwritten today, section 2).
5. One resolver for every content-addressed kind; a kind is defined by its
   identity rule.
6. No identity change, with one exception. Every existing lineage id and
   vector id reproduces unchanged. The committed Si configuration is re-keyed
   once, because its uid depended on the sign of a rounding residue (section
   7); it keeps its former uid as an alias, so every lineage citing it keeps
   its id and resolves.

## 1. Starting point (0.1.3)

- `omai/configurations.py` is the record layer of the `Structure` node: one
  file per structure under `docs/data/configurations/`, keyed by a
  content-addressed canonical uid (spglib-standardized primitive cell,
  rounded, sorted, sha256), an append-only provenance list, a dedup gate that
  appends provenance on an exact match and flags a physically equivalent but
  not identical cell for a human, and a file pointer `{path, sha256}` above
  1000 atoms. No vector pins a committed configuration's uid; the tests check
  invariances only.
- `Structure` and `Potential` are nodes of the Sources tier. `Potential` is
  described as the Born-Oppenheimer potential of the material, an opaque
  label, has no record layer, and is in `_NON_EVIDENCE_NODES`.
- Committed instances already cite a potential as
  `conditions.potential_sha256` (the kaldo and phono3py Si.tersoff instances,
  sha256 `52a93e90...`, and the kaldo vector in `lineage_ids.json` and
  `records.json`), and `cross_code.py` counts `potential` among the
  conditions that must match for two codes to compare.
- `index/codes/<code>.json` (representation, lineage_version, map_version,
  covers) is generated by `omai.index_data` and never hand-edited;
  `omai/representation/credits.py` holds citation, DOI, licence and URL. No
  release of any code is registered.
- A record's `execution.registry` rows are `{id, name, spdx, license_source,
  source, version}`, `version` nullable when the code is pinned by digest
  alone. Shipped vectors cite gpumd `3.9.5`; the proof record in
  `omai/vectors/records.json` cites `quantum-espresso` at `qe-7.5` and
  `qe-d3q` at `q-e-7.5`, row ids that were not representation ids then
  (`quantum-espresso` now resolves as an alias of `qe`, and `qe-d3q` is the
  representation of D3Q and thermal2, with `q-e-7.5` registered).
- `omai.lineages._validate_configuration` refuses a lineage whose
  `material.configuration` is not a committed record.
- `omai.gates` validates map contributions (log operations against the
  materialized map), not records.
- `map_version` has two meanings: the store head in index files, and the
  legacy read key for `lineage_version` in `FORMAT_DESCRIPTOR.wire`.
- Versioning (README): a change to the lineage id, the canonical JSON or a
  vector id is breaking; a schema field, a renderer or a vector is minor.

## 2. One resolver; configurations keep their API

- `omai/evidence.py` holds the kind table `{kind: (directory, uid path)}` and
  `resolve(kind, uid, roots)`. The identity functions stay with their kinds:
  `canonical_uid` in `omai.configurations` (it needs spglib) and `model_uid`
  in `omai.evidence`. `configurations.py` is not refactored: its API, slug
  rule, `files: {path, sha256}` and its overwrite of `external_ids` stay as
  they are in 0.2.0; its one identity change is the signed-zero rule
  (section 7).
- A record keeps former uids beside its uid under `aliases`; `resolve`, the
  configuration check in `omai.lineages`, `configurations.load` and the
  playground match any of them, and the registry maps each alias to its
  record.
- Two kinds: `configuration` (identity: `canonical_uid`) and `model`
  (section 3).
- A kind is defined by its identity rule. A model record names its node
  (`node`, default `Potential`), so a CALPHAD database (an
  `AssessedDatabase` file, the CALPHAD analog of an MLIP checkpoint) or a
  cluster-expansion coefficient file needs no new kind.
- `omai.map_data` also writes `omai/data/registry.json` (the uid of every
  configuration and model record, and from the second change every release
  with its aliases), shipped in the wheel beside `omai/vectors/` as
  package-data. The public root of `roots` is that file in an installed
  package and `docs/data/` in a source tree; a test asserts the committed file
  equals a fresh build. Overlay map contributions are validated where `map/`
  exists (a source tree or the overlay host), since the wheel ships no map
  log.
- The first change opens with a vector pinning the committed Si
  configuration's canonical JSON and uid (`7b5e77b1...`); it also catches
  spglib or pymatgen drift (section 7).

## 3. Model records (kind `model`)

Fields:

- `uid`: the identity of the files the evaluating code reads. One file (NEP,
  Tersoff, EAM, a MACE `.model`, a deployed NequIP or Allegro model, a UMA
  checkpoint): the sha256 of its exact bytes. Several files (SNAP, GAP,
  MEAM): the sha256 of the canonical JSON `{"files": [<sha256>, ...]}`,
  digests sorted.
- `node` (default `Potential`), `name`, `release_label` (optional: the
  upstream label, e.g. `nep89_20250409`), `family` (`nep`, `mace`, ...),
  `format` (e.g. `nep.txt, nep4_zbl`).
- `files`: pointers in the lineage artifact shape `{path, role, sha256,
  bytes, url?}`; role `model` for a file the uid covers, `training_state` for
  one it does not (a NEP restart file, a training checkpoint, an ACE active
  set).
- `elements`: the sorted element set the model covers.
- `license`: `{spdx, license_source}`; `spdx` is an SPDX expression, a
  `LicenseRef-*` or `NOASSERTION`, read where `license_source` says.
- `citation`, `doi`.
- `provenance`: append-only `{kind, ref, detail}` entries, the configuration
  shape. A model trained by a recorded run cites its training record (`kind:
  lineage`), whose conditions hold the base model, the label set and the
  hyperparameters. A model trained elsewhere may carry them inline. A
  conversion (a MACE model converted for LAMMPS, a device-compiled NequIP
  model, a re-saved text file) and an external fine-tune are entries of kind
  `conversion` or `fine_tune` whose `ref` is the source uid.

Identity is the bytes the evaluating code reads. It never merges two models.
It splits byte-different copies of one model, which the registrant declares
with a `conversion` provenance entry; nothing detects them (the commons holds
no weights, and loading a pickled model executes code).

What a uid does not fix: the uid identifies parameters, not the energy
surface. A head or task selection (multi-head MACE, a UMA task), the
evaluation dtype, and a dispersion term added at run time (GPUMD `dftd3`) are
separate lineage conditions the representation declares (a committed instance
already carries `model: "MACE-MH-1 matpes_r2scan"`).

Citation keys: a lineage cites the model it evaluates as
`conditions.potential_sha256` and, for a training run, the model it starts
from as `conditions.base_potential_sha256`; each value is the bare uid, 64
lowercase hex, no `sha256:` prefix. The commons fixes both keys for every
representation, so one model compares across codes and the validator finds
every model citation. The model check reads these keys only: a potential hash
that appears in free text (a `source.detail`) is not a citation, and its model
is registered when a record cites it. Each node a model record serves has
fixed citation keys; `Potential`'s are these two, and a later node fixes its
keys with its first record. `SetVoltage` is the exception: its key,
`conditions.calibration_sha256` (the calibration a set-voltage device model
reads), is fixed by ruling, because that calibration stays private to its
owner and is never registered; a record citing it lists it in
`unregistered`.

A training record stays on `Potential` with no value (`Potential` remains in
`_NON_EVIDENCE_NODES`); its model-file artifact pointer carries the produced
uid as its sha256, and the model record cites the training record.

Records registered with the first change (sha256 and bytes read from the
upstream files; the commons holds neither file):

- NEP89: `nep89_20250409.txt` from GPUMD v4.7, uid `75168ece...`;
  `nep89_20250409.restart` as `training_state`; licence `NOASSERTION` until
  the copyright holder states one; citation of the NEP89 paper.
- Si.tersoff: uid `52a93e90...`, cited by the committed kaldo and phono3py
  instances and the kaldo vector; Tersoff (1989) citation; licence read at its
  source (`NOASSERTION` where the file states none). Every other
  `potential_sha256` value in committed data is registered before the model
  check binds.

Optional physics check, report only: a lineage whose configuration species are
not a subset of the cited model's `elements`.

## 4. Code releases

- Releases are authored as data in `docs/data/releases/<representation>.json`:
  an append-only list of `{version, tag, commit, released, spdx,
  license_source}`, plus `aliases`, the registry row ids that name the
  representation (`quantum-espresso` for `qe`). `omai.index_data` projects
  them into `index/codes/<rep>.json` and `omai.map_data` into
  `docs/data/codes.json`. The licence is read at each release, since it can
  change between releases.
- The release check lives in `omai.lineages` beside `_validate_configuration`.
  A row resolves when its `id` is a representation or an alias of one and its
  `version` equals a registered `version` or `tag`; `version: null` resolves
  only with `image_digest` or `container_digest` and only for a code with no
  registered release. `validate_light` reports unresolved rows; no omai writer
  refuses them (compute workers mint with `record_simulation`). The refusal
  sits where rows are made: an engine's manifest check refuses a row of a code
  that has registered releases unless its version is one of them.
- Backfill: the distinct (registry id, version) pairs in the shipped vectors
  and in records already minted, plus the versions engines pin today (kaldo
  2.2.1, phono3py 4.4.0, lammps 2025.7.22.4.0), each under its exact string.
  GPUMD 4.7 is registered when a producer first runs it. Codes without a
  representation yet have their rows reported, not refused.
- An engine's manifest generator reads releases and licences from the pinned
  omai, so there is one source of licence truth; its registry rows' `spdx` and
  `version` are derived from or checked against them.

## 5. Registration and privacy

- A lineage may cite any configuration uid or model uid. An unregistered uid
  is listed in a top-level `unregistered: [{kind, uid}]`, outside identity
  like `artifacts` and `mirrors`, added to the schema and to
  `FORMAT_DESCRIPTOR.record_fields`. The list states what was unregistered at
  minting; a listed uid that later resolves is checked as registered and is
  never an error.
- The validator resolves every registered uid and checks it; it accepts an
  unregistered uid only when it is listed. `_validate_configuration` changes
  accordingly: it no longer refuses a structure that is not public, it
  requires the marker. One mechanism serves configurations and models. A
  `sha256:`-prefixed configuration pin is normalized to the bare uid before it
  is compared with `unregistered` entries. `record_simulation` and
  `record_light` gain `unregistered`, `lineage_version` and `overlay_version`
  parameters; envelope members already pass extra keys through
  (`_normalize_member`), so sharing keeps the marker.
- A caller's own potential is cited by its sha256 and listed in
  `unregistered` unless it is published.
- A record carrying `unregistered` or `overlay_version` is private data: a
  host mints no public openmaterials.ai link for it, and the site's public
  short-link store refuses it unless the owner chooses.
- Registering is a pull request to the commons through its gates; it replaces
  host-internal URLs with public pointers. The host keeps the bytes of
  unregistered entries and never sends them to the commons.
- A configuration uid hashes a rounded standardized cell, so it confirms a
  guessed structure; a trained model's uid does not reveal its parameters.

## 6. Private overlays

- `overlay.json` holds `{namespace, base_graph_version}`, the public store head
  the overlay is validated against. `overlay_version` is computed, never
  stored: the sha256 of the canonical JSON `{"base": base_graph_version,
  "files": [[path, sha256], ...]}` over every overlay file except
  `overlay.json`, paths sorted.
- An overlay representation is data: the index entry shape `{representation,
  covers: [{node, uid, api, unit}]}` plus a credits row and its releases.
  Every lineage validator and writer that resolves a uid (`_validate`,
  `validate_light`, `record_light`, `record_simulation`,
  `_validate_configuration`) gains `roots: list[Path] | None` (public root
  first, then overlays); `config_dir` stays, deprecated, as a root holding
  only configurations; `configurations.py` keeps its API. `roots` also extends
  `name_to_uid` with overlay node names and the aliases of published nodes.
- Add only: an overlay's map part is a contribution `[{op, payload}]` of
  `add_node` and `add_edge` only, validated by `validate_contribution` against
  the public map at `base_graph_version` (connectivity included). An overlay
  record whose uid is public is refused (cite the public one). Identity never
  carries the namespace: every vocabulary entry an overlay adds (quantity
  tags, label keys, label values, index kinds, gauge groups and symbol
  dimensions: every registry `_check_registry` reads) goes in its
  `registry.json` (add only; a string the public registry or another loaded
  overlay holds is refused), and `validate_contribution` takes that
  vocabulary as a parameter instead of reading module constants, so a node
  keeps its uid when published. Names carry the namespace (`ns:Name`,
  `ns:code`). A published node keeps `ns:Name` as an alias that
  `_validate_lineage_node` resolves, so records minted against the overlay
  keep their ids; aliases are declared on the node in the operator layer, so
  `omai.sync` carries them into map meta and `build_graph_dict` emits them
  into `name_to_uid`. Release versions are not content-addressed: the union
  refuses one (code, version) with two commits.
- A record made against an overlay carries `lineage_version` (the write key
  `FORMAT_DESCRIPTOR` already declares) and `overlay_version`, top-level,
  outside identity.
- Namespaces: the overlay owner chooses one; the commons keeps no list (a list
  would publish who holds overlays). A host refuses duplicates among its
  accounts and the loader refuses two overlays with one namespace. An owner
  who does not want to be named uses an opaque namespace, since it survives
  publication as an alias.
- Governance (added to GOVERNANCE.md): an overlay is not a contribution;
  nothing in it is licensed to the initiative until registered by pull
  request. CC BY 4.0 has no share-alike term, so a private overlay is
  permitted; a shared record credits the map through its `lineage_version`.
  The initiative keeps no list of overlays or namespaces.
- Hosting overlays (per account, keyed by map version) is a host's concern,
  outside the commons.

## 7. Versioning and compatibility

- No lineage id or vector id changes. One configuration uid changes: the
  committed Si cell's, by the signed-zero rule below.
- Adding `unregistered`, `lineage_version` and `overlay_version` to
  `FORMAT_DESCRIPTOR.record_fields` advances `format_rules_version` and
  `lineage_version` once (index files, version.json and the badge
  regenerate).
- The schema stays closed, so a 0.1.3 validator refuses the new fields:
  producers emit them only after every validating consumer pins 0.2.0.
- Vectors added: a one-file model fixture with inline bytes and its uid, a
  two-file fixture and its manifest uid, a `training_state` companion that
  leaves the uid unchanged (the NEP89 and Si.tersoff uids are pinned in their
  records and re-read from the upstream files at registration; the commons
  holds neither file); the Si configuration's canonical JSON and uid
  `7b5e77b1` (Python only: a TypeScript consumer has no symmetry library); a
  record with the new fields whose id equals that of the same lineage without
  them; a fixture overlay shipped as one `{path: content}` JSON in
  `omai/vectors/` with its `overlay_version`; the release-check report cases.
- Signed zero: a standardized lattice can carry a residue of about 1e-16
  whose sign differs between machines, so rounding wrote it as `-0.0` on one
  and `0.0` on another, and the committed Si cell hashed to `55bf22ca` where
  it was minted and to `7b5e77b1` on Linux x86-64. `canonical_uid` now writes
  signed zero as `0.0` (lattice and molecule coordinates add `0.0` after
  rounding). The Si record is re-keyed to `7b5e77b1` and keeps `55bf22ca`
  under `canonical.aliases`; the lineage that pins `55bf22ca` keeps its id.
  The configuration tests run on Linux and macOS in CI. Before 1.0 a
  re-keying change takes the minor version; the release notes list each
  re-keyed id.
- Retraction (GOVERNANCE.md allows removal on a rights holder's request):
  model and configuration record files gain an optional `retracted` field; a
  retracted uid still resolves, so no record breaks, and it is never served as
  current.

## 8. Design decisions

1. Multi-file models: the two-case rule of section 3 (one evaluated file: its
   sha256; several: a sorted-digest manifest; training-only companions outside
   identity). A universal manifest is rejected because it breaks the committed
   `potential_sha256` pins.
2. Near-duplicate detector: none in the first version; conversions are
   declared, not detected.
3. `NOASSERTION`: registered, stated explicitly, with `license_source` naming
   where the licence was sought and `url` pointing only at the upstream
   distribution. Registering metadata redistributes no weights; whether a host
   runs such a model is the host's decision.
4. Namespaces: chosen by the overlay owner (section 6).
5. `unregistered` serves configurations as well: one mechanism, top-level.

## 9. Delivery

This document, then three library changes inside 0.2.0:

1. The signed-zero rule and the configuration-uid vector,
   `omai/evidence.py`, `omai/data/registry.json` in the wheel, the model kind
   with the NEP89 and Si.tersoff records and the citation keys. Models
   resolve; an unlisted model uid is not refused yet.
2. Authored releases with the backfill and the release check.
3. The `unregistered` marker, which binds the model check (the `SetVoltage`
   calibration key included) in the same change so no caller potential is
   refused in between; the version fields; `roots`; `registry.json` published
   under `docs/data/` with its `citation_keys`, and one private-evidence
   predicate the site shares (`docs/assets/private-members.js`, mirrored by
   `omai.evidence.private_reasons`). Then the site Worker change
   (`infra/site`) that refuses private records in the public short-link
   store. Overlays with their GOVERNANCE.md text, and retraction, follow in
   0.2.1.

Producers that mint registry rows then read releases, licences and model uids
from the pinned library.
